Decisions we made

The main technical choices, why, and what each rules out. The common thread: ship plain, fast pages, load nothing from other sites, and let automatic checks catch mistakes before visitors do.

How the site is built

Astro, built ahead of time

Accepted
Decision 1

Every page is turned into a plain HTML file when the site is built, so there is no server and nothing to run in the visitor's browser.

Why
Fast, cheap to host, and good at Markdown content.
Rules out
Next.js, Eleventy, server rendering.

Full record

No front-end framework

Accepted
Decision 5

Pages are plain Astro components, each with its own styles, sharing one set of colours and sizes.

Why
Nothing on the site needs one, and each would add weight.
Rules out
React, Vue, Tailwind.

Full record

Blog posts as Markdown files

Accepted
Decision 2

A post is a text file in the repository. The build refuses a post with a missing title or a bad date.

Why
Writing a post is just adding a file, and mistakes never reach the site.
Rules out
A hosted CMS such as Contentful.

Full record

Icons bundled at build time

Accepted
Decision 13

Technology logos come from an installed icon set and are drawn into the page when it is built.

Why
One line per icon, and no request to an icon service.
Rules out
Icon fonts, icon CDNs, pasted SVGs.

Full record

Fonts served by the site itself

Accepted
Decision 19

Inter and IBM Plex Mono are downloaded once at build time and served from the site.

Why
Faster, more private, and no exception in the security policy.
Rules out
Loading fonts from Google on every visit.

The projects page

Project details from GitHub

Accepted
Decision 16

I choose which projects to show and write their summaries. Stars, language, topics and last activity are fetched from GitHub during each build.

Why
The choice is mine; the numbers stay current on their own.
Rules out
Listing every repository. If GitHub is down, the site still builds without the numbers.

Full record

A preview instead of a link

Accepted
Decision 17

Clicking a project opens a preview window, filled in ahead of time, with a "View on GitHub" link.

Why
The browser's own dialog handles the keyboard and focus correctly for free.
Rules out
Embedding GitHub, which it forbids. Without JavaScript the previews can't open, so a plain list of links appears instead.

Full record

Project pictures kept in the repo

Accepted
Decision 18

Each project's picture is a file in the repository, served by the site.

Why
GitHub's image service limited requests, which left broken images on the page.
Rules out
Linking to GitHub's images. A new project needs a picture, and a check enforces it.

Full record

Hosting and security

Cloudflare Pages, published from Git

Accepted
Decision 3

Every push is built and published by Cloudflare: the dev branch to a preview address, master to the live site.

Why
A generous free plan, with security and the address in one place.
Rules out
Vercel, Netlify, publishing by hand. The build runs the checks first, so a failing check stops the publish.

Full record

A strict security policy

Accepted
Decision 14

The site tells browsers to load nothing from anywhere but itself, and not to let other sites frame it. The policy is written out with every build and checked against the result.

Why
The first attempt (decision 6) silently never worked. Checking the output catches that.
Rules out
Adding an outside script, font or image without changing the policy on purpose.

Full record

One place for page addresses

Accepted
Decision 7

A single function turns a post's file name into its web address, used everywhere an address is made.

Why
The blog list and the post page can never disagree, so links can't silently break.
Rules out
Copying the address rules into a page.

Tools, tests and checks

pnpm for packages

Accepted
Decision 4

Packages are installed with pnpm, and only two of them are allowed to run install scripts.

Why
Fast, strict, and a cheap defence against a malicious package.
Rules out
npm and Yarn in this repository.

Full record

Strict TypeScript

Accepted
Decision 12

The code and the page templates are type-checked strictly before anything merges into the live branch.

Why
It catches a missing value before it shows up as "undefined" on a page.
Rules out
TypeScript's new native compiler, until Astro's checker supports it.

Full record

Vitest for fast tests

Accepted
Decision 8

Quick tests of functions and of rendered pages, run on every push.

Why
It understands Astro with no extra setup.
Rules out
Jest, Node's built-in test runner.

Full record

Playwright in real browsers

Accepted
Decision 9

Tests that click through the site in Chrome, Firefox, Safari's engine and a phone-sized Chrome, plus automatic accessibility scans.

Why
The only tool that also covers Safari's engine.
Rules out
Cypress.

Full record

Four kinds of test, kept apart

Accepted
Decisions 10 and 15

Functions, rendered pages, the finished build, and real browsers. The folder a test is in decides which kind it is.

Why
Fast tests stay fast, and the slow browser tests run only where they're needed.
Rules out
Mixing kinds in one folder.

Record 10 · Record 15

GitHub Actions, light then thorough

Accepted
Decision 11

A push to dev runs the quick checks. A pull request into master runs everything, including the browser tests for the pages it touched.

Why
Day-to-day pushes stay quick; the thorough check sits where it matters.
Rules out
Merging into master with failing checks.
